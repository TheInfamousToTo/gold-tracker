# Gold Tracker — AI Signals and UI Rework

**Date:** 2026-08-23
**Status:** Approved for planning
**Branch:** `feat/ai-signals-and-ui-rework`

## Purpose

Gold Tracker records gold purchases and values them against spot prices. Two things
are missing. The application has no AI capability of its own — the `signals_log`
table exists, and the UI renders whatever is in it, but nothing in this repository
ever writes a row. And the frontend is a single 493-line `App.jsx` with no charts,
which makes the one question the application exists to answer — am I above or below
my entry prices, and is now a reasonable time to act — impossible to see at a glance.

This design adds a buy/sell/hold recommendation generated by the Go backend, and
restructures the frontend around it.

## Constraints

**No metered API spend.** The Anthropic Messages API bills per token and is not
covered by a Claude subscription. The owner's requirement is that this integration
run on their existing subscription. The only path that satisfies that is invoking
the Claude Code CLI in headless mode (`claude -p`), authenticated with a long-lived
OAuth token from `claude setup-token`, supplied as `CLAUDE_CODE_OAUTH_TOKEN`.

Consequences accepted as part of this design:

- The API container must ship Node and `@anthropic-ai/claude-code` alongside the Go
  binary. The image grows from roughly 25 MB to roughly 250 MB.
- Each generation spawns a process and takes seconds, not milliseconds.
- Rate limits are the subscription's session and weekly limits, shared with the
  owner's interactive Claude Code usage. This is a direct argument for the daily cap
  described below.
- The model is pinned with `--model claude-opus-5`.

**Prices arrive from n8n.** An existing n8n workflow writes into `gold_prices`. The
backend adds no price scheduler and no external price API. Recommendation quality is
bounded by the density of that feed, and the prompt states the observed data density
explicitly so the model hedges rather than inventing a trend from sparse points.

**Single user, self-hosted.** The application has no authentication and is not
exposed publicly. This justifies the simplicity of the single-flight lock and the
in-process status tracking; neither would survive horizontal scaling, and neither
needs to.

## Architecture

### New Go package: `backend/internal/ai/`

| File | Responsibility |
| --- | --- |
| `runner.go` | A `Runner` interface and a `CLIRunner` implementation that spawns the `claude` process. The interface exists so that no test spawns the real CLI. |
| `prompt.go` | Builds the prompt from price history and holdings. Owns the fencing of untrusted user text. |
| `parse.go` | Extracts and validates the JSON verdict from the CLI's output. Has no knowledge of the database. |
| `service.go` | Orchestrates gather, prompt, run, parse, and persist. Owns the single-flight lock, the run status, and the daily cap. |

Existing packages change as follows. `internal/repository/signals.go` gains
`CreateSignal` and `GetLatestSignal(source)`. `internal/api/handlers.go` gains
`GenerateSignal` and `SignalStatus`. `internal/model/models.go` extends `SignalLog`
with the new columns. `cmd/main.go` constructs the AI service and registers two
routes. Nothing else in the backend is touched.

### Configuration

Every value is optional, so the application still boots with no AI configured.

```
AI_ENABLED=true
CLAUDE_CODE_OAUTH_TOKEN=<from `claude setup-token`>
CLAUDE_CONFIG_DIR=/app/.claude
AI_MODEL=claude-opus-5
AI_TIMEOUT_SECONDS=180
AI_AUTO_MIN_HOURS=24
```

When `AI_ENABLED` is false or the token is absent, `POST /api/signals/generate`
returns `503` with a reason string, and the UI renders a "not configured" state
rather than a button that fails when pressed.

### API surface

| Method | Path | Behavior |
| --- | --- | --- |
| `POST` | `/api/signals/generate` | Starts a run. Returns `202` on start, `409` if a run is already in flight, `503` if AI is not configured. |
| `GET` | `/api/signals/status` | Returns `{running, started_at, last_error, last_generated_at}`. |

Generation is asynchronous. A synchronous request would hold an HTTP connection open
for up to three minutes through nginx, which is a timeout waiting to happen. The UI
polls the status endpoint every two seconds while a run is in flight and refetches
the signal list on completion.

## Data flow

1. **Trigger.** Either `POST /api/signals/generate` from the UI button, or a
   successful `CreatePrice` where the newest signal with `source = 'auto'` is older
   than `AI_AUTO_MIN_HOURS`.
2. **Gather.** The last 90 rows of `gold_prices`, the portfolio totals, and holdings
   aggregated by karat. Individual item rows are not sent — the model needs the shape
   of the position, not the owner's per-item notes.
3. **Run.** `exec.CommandContext` invokes
   `claude -p <prompt> --output-format json --model $AI_MODEL` with stdin closed,
   the configured timeout, and `CLAUDE_CODE_OAUTH_TOKEN` in the process environment.
4. **Parse and validate.** See below.
5. **Persist.** Insert into `signals_log` with `model` and `source` populated.

Automatic generation runs in a goroutine started after the `POST /api/prices`
response has been written. A failure there is logged and otherwise silent. It must
never fail the price write that n8n depends on.

## The three hardening requirements

### Prompt injection

`vendor` and `notes` are free text the owner types, and would otherwise be
interpolated into a prompt. Three layers of defense:

- The aggregate path excludes those fields entirely. They are not sent.
- Where user-controlled text must appear, it is placed inside a delimited block, with
  the delimiter string stripped from the payload first, and an instruction that
  content between the markers is data to be described and never instructions to be
  followed.
- The verdict is validated against a closed enum regardless of what the model
  returns, so even a successful injection cannot write an arbitrary `signal_type`.

### Structured output

Headless CLI invocation has no equivalent of the API's `output_config.format`, so
the schema is enforced on our side. The prompt specifies exactly:

```json
{
  "signal": "BUY|SELL|HOLD",
  "confidence": 0.0,
  "reasoning": "...",
  "horizon_days": 30,
  "key_factors": ["..."]
}
```

`parse.go` extracts the first balanced `{...}` object from the CLI envelope's
`result` field, unmarshals it into a typed struct, and validates that `signal` is one
of the three permitted values, `confidence` falls within `[0, 1]`, and `reasoning` is
non-empty and shorter than 2000 characters. Malformed output is retried once with a
stricter instruction. A second failure records the error in the run status and writes
nothing. A partially parsed verdict never reaches `signals_log`.

### Schema columns

`signals_log` gains `model TEXT` and
`source TEXT NOT NULL DEFAULT 'manual'` with values `manual`, `auto`, or `n8n`.
Without `source`, the daily cap cannot distinguish its own automatic signals from
the owner's button presses; without `model`, there is no record of what produced a
recommendation.

The change is additive and loses no data. It is applied two ways so that both fresh
and existing installations converge: an idempotent `ADD COLUMN IF NOT EXISTS`
executed at repository startup, and the same columns added to the schema heredoc in
`setup_gold_db.sh`. This work also creates the `migrations/` directory that the
README already claims exists.

## Frontend

### Structure

```
src/
  api/client.js            fetch wrapper; one place that defines the error shape
  lib/format.js            fmt, fmtDate, karat helpers
  hooks/useGoldData.js     portfolio, prices, signals, and refresh
  hooks/useSignalRun.js    generate plus status polling
  components/
    layout/     AppShell, NavTabs
    ui/         Card, Badge, Button, Field, Toast, EmptyState, Skeleton
    holdings/   StatGrid, HoldingsTable, HoldingRow
    forms/      ItemForm, PriceForm
    market/     PriceChart, PriceHistoryList
    signals/    SignalPanel, SignalCard, GenerateButton
  App.jsx                  tab state only
```

### Charts

Recharts is added as the only new frontend runtime dependency. Two views:

- A 24K BHD-per-gram line chart with the owner's purchase prices drawn as reference
  dots. This is the view that answers whether current spot sits above or below the
  existing entries, which is the question the application exists to answer.
- A karat allocation breakdown of the portfolio.

### Bugs fixed as part of this work

- `frontend/src/App.jsx:392` calls `handlePriceSubmit`, which is never defined. The
  manual price entry form throws a `ReferenceError` on submit. The handler is
  implemented in `PriceForm`.
- `editingId` state exists but nothing renders a control that sets it, so
  `PUT /api/items/:id` has no caller from the UI. An edit action on each holdings row
  loads the item into the form and issues the update.

### Visual direction

The redesign goes through the `frontend-design` skill rather than restyling ad hoc.
Interface copy is rewritten in plain language: the current text ("Neural Analysis
Active", "Position liquidated", "Enterprise Assets", "Awaiting Neural Processing")
reads as marketing over a personal tracker.

## Error handling

Each failure mode maps to a distinct message exposed through
`GET /api/signals/status`: CLI binary not found, token missing or rejected, non-zero
exit, context timeout, and JSON validation failing twice. The UI renders the message
in the signals panel, where it persists, rather than in a toast that disappears
before it is read.

## Testing

Backend, table-driven Go tests with the `Runner` interface faked:

- `parse.go` against malformed, truncated, and hostile CLI output.
- `prompt.go` for delimiter stripping and correct fencing of user text.
- The daily cap at its boundary condition.
- The single-flight lock under concurrent calls.

Frontend has no test infrastructure today. Vitest is added, covering `lib/format.js`
and `api/client.js`. Full component testing is a larger commitment than this task
warrants and is deliberately out of scope.

## Out of scope

- Any automatic price feed in the Go backend. n8n owns that.
- Authentication, multi-user support, and anything that assumes more than one
  backend replica.
- Backfilling historical prices.
- Component-level frontend tests.
